# 🏛️ MiniSeek Architecture & System Specification

> **The Model Proposes. The Harness Validates. Python Executes.**

This document details the architectural principles, invariants, validation pipelines, and data flow of MiniSeek.

---

## 1. Design Invariants & Philosophical Rules

1. **Zero Direct Execution Authority**:
   Large and small language models are probabilistic text predictors. MiniSeek strictly forbids granting the model direct execution authority over the filesystem, system shells, or network APIs.

2. **Zero Model Mathematics**:
   Small models (and even large cloud models) hallucinate arithmetic operations with high confidence. In MiniSeek, the model is strictly limited to extracting raw semantic strings (e.g. `"Total: $42.50"`), while Python parses them into `decimal.Decimal` objects and computes all subtotals, tax rates, and averages with 100% precision.

3. **Zero Path Authority**:
   When categorizing files, the model never returns a filesystem path. It outputs only a predefined semantic category token (e.g. `Receipts_Invoices`). Python deterministically constructs destination paths within the approved sandbox.

4. **Explicit Model Abstention as a First-Class State**:
   When evidence is ambiguous or confidence is low, the model is instructed to output `NEEDS_REVIEW`. The harness translates this to an explicit **NO MOVE** invariant, excluding the file from filesystem proposals and escalating it for human audit.

5. **The Prime Undo Invariant**:
   *MiniSeek never overwrites newer user files merely to undo itself.*

## 3. The Canonical 6-Layer Validation Pipeline

Every output generated by the local language model must traverse six sequential validation gates before being accepted as a proposal:

```
[MODEL RAW RESPONSE]
         │
         ▼
[Layer 1: Markdown/JSON Extraction]
  Strips ```json code fences, preamble commentary, and post-generation chatter.
         │
         ▼
[Layer 2: Safe Syntax Repair]
  Fixes common small-model JSON syntax quirks (trailing commas, unescaped quotes).
         │
         ▼
[Layer 3: JSON Structural Parse]
  Deterministic deserialization via Python standard json.loads().
         │
         ▼
[Layer 4: Schema Validation]
  Validates required keys, value data types, and bounded confidence ranges [0.0, 1.0].
         │
         ▼
[Layer 5: Semantic Domain Validation]
  Ensures the proposed category exists in the allowed whitelist.
         │
         ▼
[Layer 6: Security & Safety Boundary Verification]
  Checks for directory traversal attacks (../../etc), null-byte injections,
  and verifies that the destination path resides strictly within the canonical root.
         │
         ▼
[VALIDATED PROPOSAL]
```

### 1-Retry Diagnostic Guard
If an output fails at Layer 4, 5, or 6, the harness automatically intercepts the error and invokes the model exactly **once** with a diagnostic prompt containing the validation error. If the retry fails or times out, the item safely falls back to `NEEDS_REVIEW`.

## 4. Cryptographic Plan Freezing & Transactional Execution

To prevent race conditions and ensure full user observability, execution is decoupled into two discrete phases:

### Phase 1: Plan Generation & Freezing
1. The scanner traverses the target directory.
2. The categorizer generates validated proposals for each file.
3. The `PlanBuilder` constructs an immutable `Plan` object containing:
   - Unique `plan_id`
   - Deterministic `plan_hash` (SHA-256 over canonicalized JSON operations)
   - Pre-computed source paths, destination paths, file sizes, and source SHA-256 hashes.
   - List of abstained `NEEDS_REVIEW` files.
4. The plan is presented to the user via dry-run preview. Once frozen, the LLM is completely excluded from execution.

### Phase 2: Transactional Execution
1. **Strict Pre-Flight Verification**:
   - Re-verifies `plan_hash` integrity.
   - Confirms every source file still exists and matches planned size and SHA-256.
   - Confirms no destination path collides with an existing file.
2. **Deterministic Move Operations**:
   - Operations executed sequentially via Python's standard `shutil.move`.
3. **Immediate Per-Operation Verification**:
   - Confirms source path has disappeared.
   - Confirms destination file exists and matches original SHA-256 and size.
4. **Durable Manifest Persistence**:
   - Incremental updates written to `.miniseek/history/<run-id>.json` after each step, ensuring crash safety.

## 5. Reverse-Order Conservative Undo State Machine

Each recorded run can be reverted using `miniseek undo <run-id>`:

* **Reverse Sequence**: If files were moved in sequence $A \to B \to C$, the rollback processes $C \to B \to A$.
* **Conflict Isolation**:
  Before restoring a file, the engine checks:
  1. Does the destination file still match the exact SHA-256 and size created during the run? (Detects user edits).
  2. Is the original source path unoccupied? (Detects new files created at the old path).
* If any check fails, the operation is marked as `CONFLICT` and left untouched. The rest of the run continues safely.

## 6. Zero LLM Math & Untrusted Document Boundaries

In the Expense Synthesizer application:
* **Untrusted Document Delimiters**: Ingested text is enclosed in `<document_content>` tags to isolate potential prompt injections.
* **Extraction vs Computation**:
  ```python
  # Model extracts raw string token:
  extracted_string = "Total: $1,450.75"
  
  # Python executes exact Decimal normalization:
  amount = Decimal("1450.75")
  ```
* **Multi-Factor Duplicate Grouping**: Transactions across files are only flagged as potential duplicates when all four dimensions match: `(vendor, date, amount, currency)`.
* **Multi-Currency Isolation**: USD, EUR, and INR amounts are maintained in strictly isolated accounting ledgers to prevent invalid cross-currency additions without verified exchange rates.
